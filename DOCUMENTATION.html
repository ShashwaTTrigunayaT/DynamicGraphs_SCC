How to get Algorithm Time: The CUDA program now prints it directly! Every run outputs:

>>>ALGO_TIME: 31.91ms (CUDA_PROFILE_TOTAL 43.74ms - H2D/D2H 11.83ms)

No nsys needed — the program wraps every hot-path cudaMemcpy call with std::chrono timers to measure transfer time, then computes ALGO_TIME = CUDA_PROFILE_TOTAL - transfer_time. This is Option 3 (excludes only H2D/D2H transfers, includes everything else).

🚀 Attempt 7: GPU-Only FB (Jun 25) ✅ BIG WIN — Eliminates H2D/D2H in FB phase

Problem: The FB phase downloaded every WCC component's node list from GPU to host (D2H), then re-uploaded as a flat buffer (H2D) each level. For ljournal-2008 with 8 FB levels, this added 40ms of pure transfer overhead.

Fix: Two changes in run_gpu_fb:

  1. Initial level: Use WCC big buffer directly via pointer arithmetic (w->d_set_nodes - wcc_buf) instead of downloading nodes to host. No D2H of node data.
  2. Subsequent levels: Keep scatter results in d_bulk_buf on GPU. Build next iteration's metadata (starts/sizes/colors) from prefix sums on host. Only upload tiny metadata each level — no bulk D2H→H2D round-trip.

Result: ljournal-2008 H2D/D2H: 40.40ms → 0.35ms (-99%). TOTAL: 69.26ms → 28.69ms. soc-LiveJournal1 TOTAL: ~57ms → 23.99ms.

🔍 Optimization Attempts Detail

Attempt 4: SMEM Hash Table in GPU_FB ✅ BIG WIN

Problem: The gpu_fb_batch_kernel did for (int j = 0; j < comp_size; j++) if (smem_nodes[j] == k) for every BFS neighbor — O(comp_size) per lookup. With 2048-node components and dense edges, this exploded to 70ms on web-Stanford.

Fix: 4096-slot Fibonacci hash table in SMEM. Hash: (key * 2654435761u) >> 20. 4096 slots × 8 bytes = 32KB in SMEM (total 45.5KB, under 48KB ✓).

Result: web-Stanford FB: 70.68ms → 16.18ms (-77%). TOTAL: 99.65ms → 49.27ms.

Attempt 6: ALGO_TIME Inline Tracking ✅ No more nsys for Algorithm Time

Problem: Getting Algorithm Time required running nsys (takes ~10 seconds), parsing output, and manually computing kernel + launch + memset sums.

Solution: Added CUDA_TIMED_MEMCPY macro that wraps every hot-path cudaMemcpy call with std::chrono timers (not CUDA events — those added ~10ms overhead). Accumulates total H2D/D2H transfer time in g_algo_memcpy_ms. The program prints >>>ALGO_TIME: X.XXms (CUDA_PROFILE_TOTAL Y.YYms - H2D/D2H Z.ZZms) at the end of every run.

Result: Algorithm Time is now a first-class output of every run. No nsys needed. Just grep for ALGO_TIME.

Attempt 5: BFS Neighbor Parallelization ✅ BIG WIN

Problem: wiki-Talk had 459 BFS levels × 1-5 nodes/frontier × 1 thread scanning neighbors = ~26ms.

Fix: All 256 threads share the frontier work. Each thread claims a different neighbor via atomicCAS.

Result: wiki-Talk GLOBAL_BFS: 26.8ms → 3.0ms (-89%).

🐛 Known Issues

🔴 Issue 1: Persistent TRIM1 Kernel — grid.sync() Deadlock

Code preserved but disabled. Blocks exit at different iterations (data-dependent). Not fixable without restructuring.

🔴 Issue 2: gm_graph Heap Corruption

Fix: exit(0) at end of main skips destructors.

🟡 Issue 3: OpenMP Method 2 Crashes on Large Graphs

Use method 1 for OpenMP on large graphs (skips TRIM12/WCC, correct SCC count).

🟡 Issue 4: TRIM12 & WCC Slower on GPU

Small workloads (8K-50K nodes) where kernel launch overhead dominates. Not worth optimizing — tiny absolute times.

🟡 Issue 5: cuda_get_new_color() Not Thread-Safe

Uses non-atomic _cuda_color_used++.

⚪ Issue 6: ALGO_TIME numbers need to be collected

ALGO_TIME is now printed inline by every run. Run each of the 8 datasets and fill in the results table with the ALGO_TIME values.
