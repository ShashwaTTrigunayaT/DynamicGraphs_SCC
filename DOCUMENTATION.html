⏱️ Timing Terminology

CUDA times are split into two columns for fair comparison:

TermIncludedExcludedCompared to OpenMP?
Algorithm Time (GpuKernel) GPU kernel execution + cudaLaunchKernel + cudaMemset/MemsetAsync
≈ what the GPU actually computes		 cudaMemcpy (H2D/D2H), cudaDeviceSynchronize, cudaStreamSynchronize
≈ driver overhead that OpenMP doesn't pay		 ✅ Yes — fair comparison against OpenMP's pure compute
CUDA Runtime Every CUDA API call: kernels + syncs + memcpys + memsets + launches
≈ total wall time you experience		 Graph loading (file I/O + CSR build), one-time cudaMalloc for graph upload ❌ No — includes driver overhead that skews comparison
OpenMP Pure CPU computation (parallel for loops) Graph loading (file I/O + CSR build) Baseline

How to get Algorithm Time: Run nsys profile --stats=true and sum the cuda_gpu_kern_sum (all kernels) + cuda_api_sum (cudaLaunchKernel + cudaMemset + cudaMemsetAsync only). The remaining API time in cuda_api_sum is syncs + memcpys (driver overhead).

🔍 Optimization Attempts Detail

Attempt 4: SMEM Hash Table in GPU_FB ✅ BIG WIN

Problem: The gpu_fb_batch_kernel did for (int j = 0; j < comp_size; j++) if (smem_nodes[j] == k) for every BFS neighbor — O(comp_size) per lookup. With 2048-node components and dense edges, this exploded to 70ms on web-Stanford.

Fix: 4096-slot Fibonacci hash table in SMEM. Hash: (key * 2654435761u) >> 20. 4096 slots × 8 bytes = 32KB in SMEM (total 45.5KB, under 48KB ✓).

Result: web-Stanford FB: 70.68ms → 16.18ms (-77%). TOTAL: 99.65ms → 49.27ms.

Attempt 5: BFS Neighbor Parallelization ✅ BIG WIN

Problem: wiki-Talk had 459 BFS levels × 1-5 nodes/frontier × 1 thread scanning neighbors = ~26ms.

Fix: All 256 threads share the frontier work. Each thread claims a different neighbor via atomicCAS.

Result: wiki-Talk GLOBAL_BFS: 26.8ms → 3.0ms (-89%).

🐛 Known Issues

🔴 Issue 1: Persistent TRIM1 Kernel — grid.sync() Deadlock

Code preserved but disabled. Blocks exit at different iterations (data-dependent). Not fixable without restructuring.

🔴 Issue 2: gm_graph Heap Corruption

Fix: exit(0) at end of main skips destructors.

🟡 Issue 3: OpenMP Method 2 Crashes on Large Graphs

Use method 1 for OpenMP on large graphs (skips TRIM12/WCC, correct SCC count).

🟡 Issue 4: TRIM12 & WCC Slower on GPU

Small workloads (8K-50K nodes) where kernel launch overhead dominates. Not worth optimizing — tiny absolute times.

🟡 Issue 5: cuda_get_new_color() Not Thread-Safe

Uses non-atomic _cuda_color_used++.

⚪ Issue 6: Algorithm Time unknown for 6 datasets

Need nsys output to compute fair kernel-only comparison against OpenMP.
