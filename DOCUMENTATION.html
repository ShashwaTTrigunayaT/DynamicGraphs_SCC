🚀 nsys Profiling Session

We used NVIDIA Nsight Systems (nsys profile) to identify hidden bottlenecks that CUDA event timing alone can't show — specifically API overhead (cudaDeviceSynchronize, cudaStreamSynchronize, cudaMemcpy) vs. actual kernel execution time.

Key nsys findings on wikipedia-20070206:

CategoryTimeInsight
GPU kernel time31.4ms (67%)trim1 (15.3ms) + BFS FW (5.6ms) + BFS BW (4.9ms) + WCC (3.4ms) + others
cudaDeviceSynchronize21.2ms (110 calls)193μs each — most of this IS waiting for the kernel to finish (not overhead)
cudaStreamSynchronize13.4ms (480 calls)28μs each — per-level BFS sync, unavoidable with per-level launches
cudaMemcpy H2D31.8ms (28 calls)13.7ms = one-time graph upload (180MB CSR), not in hot path

🔍 Today's Optimization Attempts

Attempt 1: TRIM1 Stream Sync ❌ (reverted)

Hypothesis: 71 TRIM1 iterations × 190μs sync overhead = ~13.5ms waste. Replace cudaDeviceSynchronize with cudaMemcpyAsync to pinned memory + cudaStreamSynchronize on a dedicated stream.

Result: Zero improvement. TRIM1 remained at 15ms. The nsys profile confirmed that the 200μs/pass was kernel execution time (reading d_Color + neighbor lists for 1.6M nodes), not sync overhead. The sync overhead was only ~6μs/pass. Lesson: profile first, optimize second.

Attempt 2: Progressive Compact Rebuild ❌ (reverted)

Hypothesis: Each TRIM1 pass scans all 1.6M compact nodes. If we rebuild the compact list between passes (filtering out SCC_FOUND nodes), later passes scan fewer nodes and run faster.

Result: Made TRIM1 worse (15ms → 25ms). Each rebuild calls create_trim1_compact() which does cudaMemset + kernel launch + cudaDeviceSynchronize + cudaMemcpy — costing ~200μs per rebuild. That's the same cost as a full scan pass, so the rebuild overhead cancels out the scan savings. Lesson: host-side sync between passes is too expensive to make progressive compact worthwhile.

Attempt 3: Persistent TRIM1 Kernel (Cooperative Groups) ❌ (hangs)

Hypothesis: Run all 71 TRIM1 passes in a single persistent kernel launch with Cooperative Groups grid.sync(). This would allow progressive compact without paying the host sync penalty.

Result: Kernel hangs. The Cooperative Groups grid.sync() barrier requires ALL blocks in the grid to reach each sync point. But blocks exit the kernel's main loop at different iterations (when their nodes are all trimmed), so they never reach subsequent grid.sync() calls — causing indefinite deadlock. The kernel code is preserved in the file but the host function uses the proven per-level loop. Lesson: Cooperative Groups grid.sync() doesn't work with data-dependent early exit conditions.

Attempt 4: SMEM Hash Table in GPU_FB ✅ BIG WIN

Hypothesis: The gpu_fb_batch_kernel does for (int j = 0; j < comp_size; j++) if (smem_nodes[j] == k) for every BFS neighbor visit — O(comp_size) per lookup. For 2048-node components with dense connectivity, this means millions of iterations through the linear scan.

Fix: Replace with a 4096-slot Fibonacci hash table in shared memory. Hash function: (key * 2654435761u) >> 20 — multiply by golden ratio, take top 12 bits. 4096 slots at 0.5 load factor (for 2048 nodes) gives ~1.5 expected probes per lookup.

Implementation details:

  • Added smem_hash[4096] (16KB) after existing SMEM layout — total SMEM: 45.5KB, under 48KB limit ✓
  • Hash build phase: each thread inserts its nodes using atomicCAS for concurrent linear probing
  • All 3 linear searches replaced: 1 in FW BFS + 2 in BW BFS (fw_color and base_color paths)
  • Pivot search (runs once per component) kept as linear scan — negligible cost

Attempt 5: BFS Neighbor Parallelization ✅ (BIG WIN, earlier commit)

Problem: On high-diameter graphs (wiki-Talk, wikipedia-20070206), the GLOBAL_BFS pivot often has only 1-2 neighbors. The kernel launched 256 threads but only 1-2 did meaningful work — the rest idled. Then it took 459+ BFS levels × 1-5 nodes/level = ~26ms on wiki-Talk.

Fix: Expand each BFS level's work by scanning all neighbors of the entire frontier set in parallel. Single thread per node → 256 threads sharing the work. Each thread claims a different neighbor via atomicCAS. This means even with a 1-node frontier (like wiki-Talk's deep levels), all 256 threads process its out-edges simultaneously.

Result: wiki-Talk GLOBAL_BFS: 26.8ms → 3.0ms (-89%). wikipedia-20070206 GLOBAL_BFS: similar improvement, TOTAL from 118ms → 44ms.

🐛 Known Issues

🔴 Issue 1: Persistent TRIM1 Kernel — grid.sync() Deadlock

The Cooperative Groups persistent kernel in scc_cuda_trim1.cu is preserved but disabled. Blocks exit at different iterations (data-dependent), preventing grid-level synchronization. Not fixable without restructuring the algorithm.

🔴 Issue 2: gm_graph Heap Corruption

Fix: exit(0) at end of main skips destructors.

🟡 Issue 3: OpenMP Method 2 Crashes on Large Graphs

Method 2 segfaults on very large graphs during TRIM12 phase. Use method 1 for OpenMP on large graphs. Method 1 skips TRIM12 and WCC but still gives correct SCC count.

🟡 Issue 4: TRIM12 & WCC Slower on GPU

Small workloads (8K-50K nodes) where GPU kernel launch overhead dominates. TRIM12 is 3.3× slower than OpenMP (0.77ms vs 2.58ms on ljournal). WCC is 1.25× slower (3.39ms vs 4.25ms). These are tiny workloads on the critical path — not worth optimizing.

🟡 Issue 5: cuda_get_new_color() Not Thread-Safe

Uses non-atomic _cuda_color_used++.

⚪ Issue 6: Benchmark Thermal Throttling

Run CUDA standalone for accurate timing.

5. Key optimization lesson learned:
  • Profile before optimizing! nsys showed TRIM1's 200μs/pass was kernel time, not sync overhead — saving us from chasing the wrong optimization.
  • DNS (Did Not Scale): Host-side compact rebuild cost as much as a full scan pass (both ~200μs). Only in-device compact can save time.
  • Cooperative Groups grid.sync() deadlocks when blocks exit at different iterations. Not suitable for data-dependent loops.
  • SMEM hash tables work great for replacing O(n) BFS vertex searches — 4096 slots × 8 bytes = 32KB fits in 48KB SMEM alongside existing data.
